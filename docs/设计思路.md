# 现状
由于AI能力的提高，我们开始广泛使用AI来提高工作效率。现状时引入了opencode/claudecode作为开发平台，开发人员在这平台上使用大模型来辅助开发。在开发过程中，开发人员开发了不少AI工具，包括skill， agent, workflow等，但是我们现状面临以下痛点
1. 没有一个ai 工具等托管平台（一个工具箱），可以让我们调用，并且可以24小时不停机运行---- 这个痛点将在matrix项目中解决，计划使用falcon部署一个公司内部共用的托管平台
2. AI自动化程度低，现有大家写的很多AI过程大多是半自动的，状态并不保证幂等，重入需要用户介入。如果要保证幂等缺乏状态持久化的机制，开发门槛比较高
3。缺乏一个和AI交互的消息平台，现状大家仍旧主要依赖claudecode/opencode和/或AI expert suite，界面不友好，难以跟踪消息，特别在开了多个session的情况下难以管理
3.1 界面不友好，尤其是claudecode或者opencode的cli界面，实际上是非常用户不友好的，尤其对于非专业人士，这个界面基本上会让绝大多数人恐惧。（claude）
4. 无法自动重新运行，在1解决以后，依然有大量的需求，dev本人有自己的工作流需要在本地运行，此时如果中断，比如关机或者网络中断，ai工作流会被打断，不得不从头运行，尤其对于长时间的工作流，比如写代码-提交- review-修订-测试-回归这种工作流，会需要好几个小时，不能关机并且需要经常性手工保持当前状态是开发中一个很大的痛点
5. 综合上述，即使对于一个有开发经验的软件工程师，使用ai来自动化日常工作，提升工作效率是都是一个痛点并且是一个学习成本很高的过程，对于salesforce产品的最终用户，这更是一个说起来容易实现起来却没有可用的工具，是一个几乎无法完成的任务。导致现在AI在最终用户手中，基本上仍旧等同于chatbot

# 设想
设想是建立一个异步分布式的ai工具编排器，包括以下几个层次：
## UI层
提供一个简明易用的面向工作流的UI层，作为agent回叫的用户界面，能够及时通知用户工作流的状态，通知用户需要的进行的工作，同时允许用户通过UI驱动ai工作流或者ai agent。 https://github.com/salesforce-internal/tcm-marketplace/tree/main/plugins/tcm-toolkit/sticky-note 是当前的一个实现，可以获取用户的work item，并且驱动ai-agent推动某个工作流。这里我们可以在此基础上扩展，可以将输入（当前是GUS item）抽象化，将驱动的agent/workflow 配置化或者ai化（让worker agent自主寻找恰当的handler）
## worker层
各种agent和skill （以下简称为worker），可以使用matrix在cloud端托管（tool box）, 运行用户远程异步调用，脱机运行。这里对worker端要求是无头（能够自主运行），幂等，允许重入和断点运行 （）。同时也应该支持这个agent运行在本机，或者其他服务器。这一点对于ai开发人员非常重要，开发人员应该能够运行自己定义的worker，或者开发中还没有部署上matrix的worker。--- 这里worker层应该是个抽象的，分布式的
### 自动发现
tool box应该推出一个discover agent，根据用户需要的功能自主在工具箱中寻找恰当的worker
## 数据层
为了保证worker的幂等和断点续传，要求有一个数据持久化的机制，包括worker的instance，版本号和url，也要有worker当前的状态，包括运行变量和回叫地址等，这些数据应该有一个存储的位置。我们可以考虑无论个人的worker或者是tool box中的worker都使用共同的存储机制，也可以考虑个人的worker在本地保留。数据存储应该包括结构化的部分（这个分布编排系统的约定），和非结构化的部分（每个worker不同的约定）

## SDK
为了统一worker在编排器中的接口，以及为了降低开发门槛，我们计划推出一个ai worker开发的SDK，设计一个agent的模版 （工作流模版.md） ，每个ai worker遵从状态机的约定，开发者使用模版，只需要负责定义worker的各种状态，每个状态下的工作任务，可能的结果和状态的迁移，需要等待或者发送的事件/消息等。而这里状态的持久化，幂等性和信号/消息等接收，传递由本系统来保证。
涉及到数据库（状态持久化），消息队列（信号和消息的发送和接收）以及其他一些外围工具，比如用户本地带有login session的cron job的设置（https://github.com/salesforce-internal/tcm-marketplace/tree/main/plugins/tcm-toolkit/scripts/job-scheduler），以及和其他外部资源的信号的注册监听和撤销（比如https://github.com/salesforce-internal/tcm-marketplace/blob/main/plugins/tcm-toolkit/scripts/watch-pr.py）， slack 消息的监听， GUS状态的监听，文档变更的监听等等

# 一期工程
一期工程，我设想是先开发面向公司内部ai开发人员的分布式编排器
现在我已经在本地实现了：
- wi-researcher和wi-worker的自动化
- 使用sticky-notes的即时人机界面
- 使用WI chatter的简单的，面向GUS WI的状态持久化
- 监听slack channel, gus 状态，PR 状态的小工具
- 面向个人的本机带login session的job scheduler

使用这些工具，我能够做到
- 同时并行处理多个（4-5）个WI
- 全自动推进WI，无需通过AI runtime比如claudecode/opencode进行交互，而通过AI反馈的信号，通过外部工具和AI交互
- 工作效率（engineer 360数据）是其他人的3倍

一期工程的目标：
- 针对WI，应该由AI来完成工作
- 人类负责做决定，审查和验收（承担责任）
- 建立ai工具箱（matrix)，使ai worker能够24小时脱机运行
- 建立ai状态的持久化
- 完善AI worker，提高处理的鲁棒性和通过skill-discover发现恰当的ai handler的能力
- 推广WI worker，提升WI的处理效率。目标是现有（大多数人通过人工和AI交互处理WI）的三倍
- 用户能够实现异步/脱机驱动，即驱动一个ai工作流以后，用户可以关机，断网，远端worker能够保证自动运行到下一步等待外部信号，本地workflow能够在本机重启时自动检测上次中断并断点重新开始执行。

# 二期工程
二期工程目标
- 建立统一的ai agent的模版，降低新worker的开发门槛
- 建立完善的消息，事件的监听，捕捉和分发功能，将更多的工作流统一到本系统中推动自动化
- 将其他salesforce工具耦合进系统，比如可以用slack接收ai消息和驱动ai 工作流，使用tableau作为工作流的输入或者输出，使用mulesoft作为管道来链接不同的worker和工作流
- 可以使用自动化处理gus wi以外的工作流
- 建立SDK，改写现有的worker，统一规范，推动自动化和降低token的消耗
- 培训FDE，了解用户需求和研究在用户推广和使用这个分布式编排的实际用例

# 远期目标
长期愿景是将本产品商业化，使用模版，图形化界面，和封装的状态持久化，消息交互和鉴权机制，大大降低用户利用已有的worker配置，定义和组装自己工作流的技术门槛
